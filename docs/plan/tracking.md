# How this project is tracked

> This document is itself an assessment artifact. Brief §26 grades *the engineering process
> you personally use*; §21 grades how AI contributions were validated; §25 grades scope
> management. A tracker abandoned on day six produces evidence for none of them.

## Decision

**`SmartRail-Project-Tracker.xlsx` is the single source of truth.** One workbook holds the
plan, the progress, the AI-usage ledger and the registers.

Why Excel rather than a markdown or YAML tracker generated by a script:

| Criterion | Verdict |
|---|---|
| Will actually be maintained daily | Excel. Familiarity beats elegance; a tracker you open beats one you admire. |
| Reads as project management to an assessor | Excel. A three-level WBS with rolled-up percentages and a Gantt is the expected artifact. |
| Produces presentation material | Excel. Dashboard and AI Summary screenshot straight into the final deck (§27). |
| Analysis of AI usage | Excel. Verdict counts, challenge rate and error-type breakdown are formulas, not hand-tallies. |
| Low ceremony to add a row mid-project | Excel. Insert, type, done. |
| Versioned, diffable history | Markdown wins — but this is the only criterion it wins, and it is not graded. |

The scripted YAML tracker that preceded this (`plan/`, `PROGRESS.md`, `docs/plan/gantt.md`)
is **retired**. Keeping both would mean maintaining the plan twice, which guarantees the two
disagree and both become untrustworthy. Delete that folder and those two generated files.

## The workbook

| Sheet | Role |
|---|---|
| **Dashboard** | Generated summary — current day, hour-weighted completion, gate status, slipped count, §21 AI evidence coverage, work-package subtask progress, daily load. The only editable cell is the yellow start date in `B3`. |
| **WBS** | The plan. Three levels: phase → work package → task. 8 / 36 / 96 rows. Only task rows are edited; the two levels above roll up automatically. |
| **Gantt** | Generated from WBS. Blue = planned, amber = in progress, green = done, red = blocked, grey = deferred. |
| **AI Policy** | Tool registry and responsibility assignment, each with the justification for *why that tool for that work* — §21 bullets 1 and 2. Also the operating rules. |
| **AI Usage Log** | One row per AI contribution. 18 columns, dropdown-driven, tool-aware. |
| **Prompt Library** | Prompts and workflows that changed the outcome — §21 bullet 3. |
| **AI Failures** | Where AI was wrong or insufficient, and where my judgment improved it — §21 bullets 5 and 6. Target 8. |
| **Modified Impl** | AI-generated implementations substantively rewritten, and why — §21 bullet 7. |
| **AI Summary** | Formulas over the log — verdict split, challenge rate overall **and per tool**, error types, the "AI was wrong" counter against the target. |
| **Decisions** | ADR index. Every row carries the justification *and* the rejected alternative. 15 pre-populated. |
| **Risks** | Risk register, R1–R10. Score auto-colours. Review every Friday. |
| **Defects** | Defect log — a QA deliverable in its own right (§23). |
| **Deferred** | Every scope cut with its reason (§25.6). |
| **Lists** | Dropdown sources. Extend at the bottom of a column. |
| **How to use** | The short version of this document, inside the file. |

### Multi-tool policy

Three tools, with authoring and review deliberately split: **ChatGPT** authors requirements,
**Gemini** reviews what it did not write, **Claude Code** implements in the repo. The governing
justification — recorded on the AI Policy sheet — is that a single model's blind spot is
invisible to itself, so the model that produced an artifact does not review it. Copilot is
explicitly *not* used, because inline autocomplete produces code you did not consciously choose
and cannot log honestly, which is the exact risk §28 warns about.

### Rebuilding the workbook

`scratchpad/build_wb.py` regenerates the whole file and is **safe to re-run**: it captures your
typed statuses, hours, notes and every log row first, then writes them back. Formulas are
recalculated and error-checked through Excel COM (`verify.ps1`) — LibreOffice is not installed
on this machine, so the xlsx skill's own `recalc.py` cannot be used.

### Cell colour convention

- **Blue text** — input. Safe to edit.
- **Black text** — formula. Do not overwrite.
- **Yellow fill** — `Dashboard!B3`, the project start date. Change that one cell and the
  entire plan, Gantt, gate dates and slip calculation reshift.

### Daily loop — under five minutes

1. Open **WBS**. Set `Status` to `Doing` on what you start.
2. On close: `Status` = `Done`, and type the **real** hours into `Act h`. The estimate-accuracy
   figure on the Dashboard is only honest if this is.
3. Log every AI contribution on **AI Usage Log**, same day.
4. Glance at the **Dashboard**. If *Slipped tasks* is red, decide now — see below.

### When the plan slips

The Dashboard counts slipped tasks and the WBS turns their titles dark red. Three legal
responses, and *choosing explicitly* is the graded behaviour:

1. **Re-date** — change `Day`, accept the knock-on.
2. **Cut** — set `Status` to `Deferred` and add a row to the **Deferred** sheet with the reason.
3. **Spend buffer** — move it to D21 and acknowledge the buffer is now smaller.

Leaving it silently slipped is not one of the options. The count stays red until you act.

### Adding work mid-project

Insert a row inside the work package it belongs to, give it the next code (e.g. `4.2.3`), set
`Lvl` to `3`, then fill the formulas in `G`, `H`, `M`, `T`, `U`, `V`, `W`, `X`, `Y` down from the
row above. Set the hidden `_parent` (R) and `_root` (S) to the parent and phase codes — the
rollups match on those, so a blank there silently excludes the task.

## AI usage: capture at the moment of work, never reconstruct

§21 wants prompts, validation, and **examples where AI was wrong**. That record cannot be
rebuilt on day 19 — memory flattens every disagreement into "it worked fine". Capture happens
in two places with different costs:

| Layer | Cost | Captures |
|---|---|---|
| **Git commit trailers** | ~0, you were committing anyway | `Task`, `AI-Role`, `AI-Verdict`, `AI-Note` on the change itself |
| **AI Usage Log row** | ~60 seconds, end of day | the full record, aggregated by the AI Summary sheet |

Enable the template once:

```bash
git config commit.template .gitmessage
```

Every commit then prompts for its AI record. Those trailers are **receipts** — timestamped in
git history, written while the work was fresh — which you transcribe into the workbook at the
end of each day. Not dual maintenance: one is capture, the other is the ledger. To collect a
day's receipts:

```bash
git log --since=yesterday --pretty=format:"%h %s%n%b" --no-merges
```

### The two columns that matter

**`Verdict`** drives the *challenge rate* on the AI Summary sheet — the share of AI
contributions rejected or materially edited. Brief §21 states outright that using AI
successfully does not mean accepting everything it generates. A project claiming heavy AI use
with a 5% challenge rate reads as unexamined.

**`What I changed or why I rejected it`** is the column an assessor actually reads. Write it
specifically enough to defend out loud:

- ✅ "Rejected its `Include` chain — N+1 across `JourneyStop` on the public departures endpoint. Replaced with a projection to a read DTO."
- ✅ "Its service-date logic used `DateTime.Today`; breaks every 23:50 departure. Implemented a GTFS-style service date."
- ❌ "Fixed AI code."
- ❌ "Worked well."

The **AI Summary** sheet tracks the count of `Was it wrong = Yes` entries against a target of
8 and tells you how many more you need. Those become the prose write-ups in
`docs/05-ai-usage/ai-was-wrong.md` — the workbook holds the record, the markdown holds the
story.

## What stays in markdown

The workbook tracks *execution*. It does not replace the reasoned documents, which are the
actual submission deliverables:

`plan.md` (strategy, scope rationale, the 59-gap register) · `docs/00-requirements/` ·
`docs/02-architecture/adr/` · `docs/03-qa/` · `docs/04-security/` ·
`docs/05-ai-usage/ai-was-wrong.md` and `prompt-library.md` · `docs/06-operations/`.

Rule of thumb: **numbers and status live in the workbook; reasoning lives in markdown.**
